# Stable LatentMoE 工程解析：Quantile Balancing、EP 通信与 896 专家路由

> 写作日期：2026-07-28｜姊妹篇：[《KDA 不是"线性注意力"这么简单》](./kda-from-formula-to-vllm.md)
> **口径声明**：本文的架构数字（896/16/2、3584、3072 等）以 [Hugging Face 官方模型卡](https://huggingface.co/moonshotai/Kimi-K3) 为准（抓取于 2026-07-28）；Quantile Balancing、SiTU-GLU、EP 训练等机制描述综合自官方技术报告（经 AlphaXiv 报告摘要转述）与 [vLLM 官方 Day-0 支持博客](https://vllm.ai/blog/2026-07-27-k3)（2026-07-27）。**"2.5× 扩展效率提升""25% 训练效率提升"均为官方自报口径**，未见独立复现。

---

## 1. 一句话版本

K3 的 MoE 不是"更多专家"这么简单：它把路由稀疏度推到 **896 选 16（激活率 1.8%）**——约为 K2（384 选 32，8.3%）的 4.6 倍——然后用三样东西稳住这个极端稀疏度：**LatentMoE**（压缩专家计算维度以省带宽）、**Quantile Balancing**（无辅助损失的负载均衡）、**SiTU-GLU**（有界激活防爆训练）。推理侧则由 vLLM 的 EP 后端与 EPLB 接管负载均衡。

## 2. 关键数字总表

| --- | --- | --- | --- |
| 路由专家数 | **896** | 384 | 官方模型卡 |
| 每 token 激活专家 | **16**（+2 共享专家） | 32（+共享） | 官方模型卡 |
| 路由激活率 | **1.8%** | 8.3% | 算术：16/896 |
| Latent MoE 维度 | **3584**（模型宽度 7168 的一半） | — | 官方模型卡 |
| 单专家 FFN 隐藏维度 | 3072 | — | 官方模型卡 |
| 每 token 激活参数 | 104B / 2.8T（3.7%） | ~32B / 1T（3.2%） | 官方模型卡 |

**注意一个反直觉点**：稀疏度翻了 4.6 倍，但每 token 激活参数占比几乎没变（3.7% vs 3.2%）。稀疏度的收益没有变成"每 token 更便宜"，而是变成了"**同样的激活预算下，总参数量（容量）从 1T 推到 2.8T**"。这是理解 K3 设计哲学的钥匙：它买的不是推理便宜，是知识容量。

## 3. LatentMoE：先压缩，再进专家

LatentMoE 由 NVIDIA 提出，K3 将其规模化。标准 MoE 中，token 以模型全宽（K3 为 7168 维）被 dispatch 给专家；LatentMoE 在进专家前先把激活**投影到 3584 维的 latent 空间**，专家在窄维度上计算，输出再投影回 7168。

```
标准 MoE:   token(7168) ──dispatch──> 专家(7168→3072→7168) ──combine──> 7168
LatentMoE:  token(7168) ──down──> latent(3584) ──dispatch──> 专家 ──combine──> up ──> 7168
```

工程收益（vLLM 博客明确点出）：

1. **专家权重带宽减半**：专家在 3584 维上读写权重，decode 阶段是 memory-bound，权重读取量直接决定 TPOT；
2. **all-to-all 通信量减半**：EP 下 token 要跨卡搬运，载荷从 7168 维压到 3584 维；
3. **同等成本下可容纳更多专家**——这是 896 这个数字在工程上成立的前提。

代价是多一对 up/down 投影矩阵（小参数、小计算），以及路由信息损失的理论风险——压缩后的表示要足以让 router 和专家分辨 token 语义，这是"Stable"二字要解决的训练问题之一。

## 4. Quantile Balancing：不要辅助损失的负载均衡

### 4.1 问题：896 选 16 时，负载失衡是一阶难题

专家越多、激活越少，router 越容易"追星"：少数热门专家吃掉大部分 token，其余专家闲置甚至退化。经典解法有两条，各有硬伤：

- **辅助损失**（Switch Transformer 一脉）：给 router 加一个均衡惩罚项。问题是要调权重系数——系数大了损害主任务（router 被迫选"不该选"的专家），系数小了压不住失衡，而且 2.8T 规模下每次调参实验都极其昂贵；
- **无辅助损失的 bias 更新**（DeepSeek-V3 一脉）：给每个专家的 router 分数加可学习/可更新的偏置，按历史负载上下调。消除了辅助损失，但偏置更新规则本身仍是启发式，且引入历史状态。

### 4.2 QB 的做法：从分位数直接推导偏置

按技术报告的转述（AlphaXiv 摘要，2026-07-27）：QB 根据**与目标专家负载相匹配的分位数**来计算每个专家 router 分数的偏置——直觉是"每个专家都应该拿到自己分数分布里 top q 的那部分 token"，q 由目标负载决定，于是每个专家**按构造**服务相同比例的 token，无需辅助损失、无需手动调均衡系数。

```
对每个专家 e：
  目标：e 恰好处理 token 总量的 1/896（路由部分）
  做法：找 e 的分数分布中对应目标份额的分位点，把偏置设到该分位点
  结果：e 保留自己 top-q 的 token，负载天然均匀
```

### 4.3 为什么这对训练系统比对论文分数更重要

报告与社区解读中一个容易被忽略的联动：负载均衡给出**静态张量形状（static shapes）**——每个专家每步处理的 token 数恒定，于是专家并行的 all-to-all 不需要主机侧同步（no host synchronization）、不触发重编译。在大集群上，host sync 是让几千张卡空等的头号杀手之一。**QB 不只是算法技巧，它是"fully balanced expert-parallel training"这套系统方案的前置条件。**

## 5. SiTU-GLU：给激活装上"护栏"

SwiGLU 在 3T 级稀疏模型上会产生数值失控：激活值长尾增长，训练后期出现 loss spike。K3 的 SiTU-GLU（Sigmoid Tanh Unit）给门控支路和上投影支路分别加光滑上限：

```
|f(x)| ≤ β₁·β₂ = 4 × 25 = 100
```

即无论输入多极端，激活坐标被钳在 ±100 以内（sigmoid/tanh 类函数天然有界，且光滑可导）。这是"Stable"的另一根支柱：QB 稳住**路由维度**的分布，SiTU-GLU 稳住**数值维度**的分布。

## 6. 推理侧：vLLM 怎么服务 896 个专家

来自 vLLM 官方 Day-0 博客（2026-07-27，权重发布当天）：

- **专家并行（EP）分片**：896 个专家切到多卡，每卡只持有 896/EP 个专家；
- **两套 MoE 后端**：TP > 1 的张量并行拓扑用 **TRT-LLM-Gen**；分离式/专家并行（DEP）拓扑用 **MegaMoE**；
- **EPLB（Expert-Parallel Load Balancing）**：运行期可选开启，**用于改善**各 rank 计算量的均衡——训练侧用 QB 追求 token 级均衡，推理侧用 EPLB 改善 rank 级均衡，两者针对的是**同一个问题在不同阶段的形态**；
- **MXFP4 原生执行**：MoE 路径直接以 MXFP4 权重计算，无需反量化。

**给部署者的翻译**：选 EP 策略时，先定拓扑（单机 TP 还是跨机 DEP），再选对应后端，然后开 EPLB 观察各 rank 负载。如果某些 rank 持续热点，优先怀疑 EPLB 未生效或 tokenizer 分布偏移（某类请求集中激活少数专家），而不是加卡。

## 7. 为什么 1.8% 激活率仍然要吃掉 1.4 TB 显存

最常见的误解："每个 token 只用 104B 参数，为什么显存要按 2.8T 准备？"

因为**稀疏性省的是计算（FLOPs），不是存储（bytes）**。推理时没人能预知下一个 token 会路由到哪 16 个专家，所以**典型的高性能部署需要让 896 个专家的权重全部驻留显存**（CPU/NVMe offload 技术上可行，但延迟会恶化一到两个数量级，只适合做验证）——这就是 MoE 的"内存-计算解耦"：

```
计算成本  ∝ 激活参数（104B）     ← 稀疏性在这里省钱
显存成本  ∝ 总参数（2.8T）       ← 稀疏性在这里一分钱不省
```

这也是 §2 说的"K3 买的是容量不是便宜"的系统对应物：**它用 2.8T 的显存账单，换 104B 的计算账单**。对比稠密模型：同等计算账单下稠密模型只有 ~100B 容量；同等容量下稠密模型的计算账单是 K3 的 27 倍。

## 8. 路由健康度的实用诊断清单

自部署或托管 K3 时，建议监控这些信号（配合 [自部署手册](./k3-selfhost-runbook.md) 的压测框架）：

| 信号 | 健康 | 异常 | 怀疑方向 |
| --- | --- | --- | --- |
| 各 rank 的 MoE 计算耗时 | 接近 | 个别 rank 持续偏高 | EPLB 未开/未生效 |
| 单请求 TPOT 突刺 | 平稳 | 周期性尖峰 | EP all-to-all 拥塞、NVLink 拓扑问题 |
| 长上下文 decode 吞吐 | 缓降 | 悬崖式下跌 | KV cache/显存挤压导致 expert offload（查 vLLM 日志） |
| 特定请求类别质量下降 | 均匀 | 某域请求明显差 | 该域 token 集中路由到少数专家，路由分布偏移 |

## 9. 尚待验证的问题（诚实清单）

1. **QB 的精确公式**：本文 §4.2 是对报告转述的还原，偏置的更新频率（每步/每窗口）、分位数估计方式（精确/近似）需读技术报告原文核对；
2. **"2.5× 扩展效率"**：官方自报，计算口径（同算力？同数据？）未见第三方复现；
3. **Latent 压缩的质量代价**：3584 维是否在某些任务上成为瓶颈，需独立评测（尤其是需要细粒度 token 区分的任务）；
4. **896 专家在不同请求分布下的真实均衡度**：QB 在训练分布下追求负载均衡，部署分布漂移后的表现需要实测。
